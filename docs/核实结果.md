## 本次实际发现并修复的验收问题

1. 同时篡改一个基线判定和相应汇总数，原语义验收仍接受。已独立重算三个区间基线，并将该协调篡改纳入负例；这属于验收器漏洞，不是已经发现核心定理反例。
2. 原 JSON 读取会接受重复字段。现拒绝重复字段和非有限数值，包括会溢出为无穷大的浮点常量。
3. 进一步约束了 CSV 的准确列集合、缺失/多余单元格、oracle 计数字段及来源绑定，不能只看一个结果布尔字段或一组自洽汇总。

新增 8 项测试。修复后的 39 项回归已执行，并在全新解包目录中再次执行，零失败、零错误、无跳过。另执行 3 项书目与专用引文宏负例，均被拒绝。保存的两套结果均执行了修复后的完整证书重放和三个基线的独立重算，消耗 15,370 项记账义务。每套 30 个解码配置、64 个累加计划，246 个科学结果文件仍逐字节一致。

真实日志位于 `results/reverification/`，包括修复前漏洞被接受的记录，没有把它们删除或改成成功。

加入 native 证据后的主稿已构建为 22 个总页，即 18 页正文、4 页参考文献；补充材料为 9 页。正文低于本项目 20 页上限（参考文献不计），不声称达到早期内部“恰好 20 页”规划。原字体、模板和页边距未改变。native 主文第 13/14 页及补充材料第 6--9 页已作视觉检查，完整 97 行 native 表能够放置，没有报告可见未解析标记。此前 16+4 页主文和 6 页补充材料的逐页审计、十三张两页联系表仍是历史记录，不能用作新稿全部页面的审计。

原六个量化生成 TeX 输入和 94 个有限语义案例未修改；三个 native 输入来自保存的真实 CPU 原始测量。79 个累加计划（原 64 加 15 控制）和 18 个安全解码器样例共保留 2,037 个 native 配对样本，另有 1,659 个 Python checker 样本。原累加案例 walker 中位配对比值为 1.483--1.979，prepare+walk 阶段和估计为 1.346--1.598；3 个阶段和慢例全部保留。prepare+walk 是分别测量阶段的和，不是计时端到端路径，不含 JSON serialization 和 Python checking。完整字节一致的 buffered/ostream 生成比较提升 29.02--39.09 倍；同一商算法的融合 prepare--walk--serialize 比较提升 19.91--26.55 倍。原案例序列化/walk 中位比为 2.7--5.2，checker 中位耗时为 106.3--323.6 us；这些不是整个检查流程加速。

原生实现保持 `(T,E,B,F)`、有序乘积商、完整层/边/最小见证和原证书 schema。优化/checked 构建输出一致，原 64 个证书及 416/1,016 边数与保存结果一致；所有原生证书和基线边均作检查。精确乘积、目标前缀及计数要求能用 int64 表示，并用 int128 检查；三种溢出控制在遍历和输出前被拒绝。公开 `results/native-cpu/` 包括单份完整一致性输出 gzip、原始样本、比较记录、compact summary、函数汇编片段和功能性绑定，不发布二进制、PDB、缓存、私有命令或本机绝对路径。这只补足本机 CPU 原生验证/解码器样例证据，绝非 GPU 或生产部署收益。
